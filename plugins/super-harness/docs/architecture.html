super-harness 架构与运行逻辑

v0.1.0依赖 harness-zh ≥ 0.2.1多路并行跑 harness-zh 的 story：每条 story 一个 worktree、一个 worker，跑完按顺序合回 sprint 分支。

它做什么整体结构一次运行长什么样调度循环：tick 怎么决定下一步一条 lane 的状态哪些 story 可以开工合流收口状态存在哪出问题时和 harness-zh 的分工命令和配置

它做什么

harness-zh 一次推进一条 story。super-harness 在它上面加一层调度：互不依赖的 story 各开一个 git worktree、各起一个 headless Claude Code 进程同时跑，跑完按完成顺序合回 sprint 分支，再在主 worktree 里串行收口。

每条 story 内部走的仍然是 harness-zh 的流水线（bmad-build-auto → build-verify → codex → follow-up review）。super-harness 只决定两件事：哪几条可以一起跑，跑完怎么合回来。

并行的部分

每条 story 的 B0 到 B3：起跑 tag、bmad-build-auto、外部 codex review、follow-up review。各在自己的 worktree 和分支上，互不干扰。

串行的部分

合流、build-sync、⑤.5 测试、epic retro。这些要写共享账本（sprint-status、deferred-work、done tag）或共用测试环境，只能一条一条来。

整体结构

决策全部交给 superh.py 的结构化输出（tick 的 JSON、各命令的 STATUS= 行和退出码），主 agent 不从日志的自然语言里猜成败。

一次运行长什么样

slot 只管 worker 的并发数。合流和收口由调度者自己做，它们串行执行时，其他 slot 里的 worker 照常在跑。

调度循环：tick 怎么决定下一步

没事可做时（wait），调度者结束当前回复。worker 是用 Bash 后台模式启动的，进程退出时 Claude Code 会唤醒调度者，所以不需要轮询。这也意味着跑的过程中不能关掉这个会话；关掉后在跑的 worker 会一起结束，下次运行时显示为 crashed，自动续作一次。

条件说明

合流

账本冲突的处理规则

每一路的 bmad-build-auto 都可能改下面三个文件，几路并行时合流几乎一定冲突。rebase 期间 ours 是 sprint 分支，theirs 是 story 的提交。

文件（artifacts 目录下一层）处理理由
sprint-status.yaml取 sprint 分支版本本 story 的状态紧接着由 build-sync 写成 done；sprint 分支上别的 story 的 done 不能丢
epic-N-context.md取 sprint 分支版本bmad-build 编译出的缓存，下次 build 会重新生成
deferred-work.md三方 union 合并追加型账本，两边新增的条目都要留
其他文件派合流冲突子 agent（每路一次）它解决不了就停在 conflict，等你处理

收口

磁盘上的事实NEXT
没有 done tag；harness-state 为 sync（或为 codex 且 marker 还没写）sync
没有 done tag；harness-state 为 tag-only（build-sync 已 commit）tag
有 done tag，测试还没完成test
有 done tag，测试已完成（有 tested 检查点，或 HEAD 里已有 <KEY>-test-result.json / skipped-<KEY>-*.md）finish
其他halt

sync 步骤中途被打断时，主 worktree 会留下 marker 或已暂存的账本改动。start-run 认得这几类文件，报 MAIN_CLEAN=resumable 放行续作；混进任何其他文件仍然 halt。

状态存在哪

文件（.git/super-harness/ 下）唯一写入者内容
run.json调度者（start-run）本次运行固定的 sprint 分支、--slots 覆盖值
lanes/<KEY>.json调度者（prepare / integrate / mark / retry / cleanup / abandon）phase、分支、worktree、rebase 的 onto、要搬的 tag、测试检查点
lanes/<KEY>.proc.jsonlaunch 包装进程pid、session id、attempt、退出码、花费
lanes/<KEY>.result.jsonworker（superh.py report）ready / blocked / failed / quota、摘要、codex 跳过原因、halt 原文
logs/<KEY>.attempt-N.*launch 包装进程渲染后的 prompt、stream-json 全量日志、stderr

每个文件只有一个写入者，避免并发写坏。harness-zh 自己的状态（harness/<KEY>/* tag、spec frontmatter、sprint-status）不变；tag 是仓库级的，任何 worktree 里打的 tag 主 worktree 都看得到。

出问题时

情况结果怎么恢复
worker 报 blocked / failed只停这一路cd <worktree> && claude --resume <session> 进去看，修好后 superh.py retry <KEY>
调度者会话结束在跑的 worker 一起结束，显示 crashed下次 /super-harness:run 自动 retry 一次
配额耗尽不再派新 lane，等在跑的结束后 halt额度恢复后 retry
合流代码冲突conflict，rebase 现场留在 lane worktree子 agent 先处理；不行就你解决并 git add，再跑 /super-harness:run
prepare / launch / 合流 / 收口中途被打断停在中间状态下次 tick 会把它送回对应步骤，从第一个没完成的地方继续
补进 lane 的文件没被 .gitignore 忽略prepare 失败，lane 记为 held按输出的 GITIGNORE= 行补 .gitignore 并提交，abandon --yes 后重新排队
build-sync halt全局 halt按 harness-zh 的 halt 模板处理

和 harness-zh 的分工

步骤在哪里执行按什么执行
B0 起跑 · B1 build · B2 codex · B3 follow-upworker，lane worktree，可并行harness-zh run.md + prompts/worker.md 的覆盖规则
合流（rebase + ff）调度者，主 worktree，串行superh.py integrate
B4 build-sync · ⑤.5 测试调度者，主 worktree，串行harness-zh run.md，每步之前问 postmerge
⑥ retro · ⑥.5 · verdict 门 · §0.A.0调度者，主 worktree，串行harness-zh run.md

super-harness 依赖项目里部署的 harness-zh（≥ 0.2.1）：run.md、harness-commit.py 的 build-verify / build-sync、harness-state.py 的续作路由，以及 harness/<KEY>/* tag 的语义。
